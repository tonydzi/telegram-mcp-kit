# Telegram для Claude Code и Codex: MCP + отдельная Telethon-рельса

Две рельсы решают разные задачи. MCP даёт агенту инструменты в текущем разговоре. Отдельный Telethon-клиент даёт скриптам и фоновым заданиям Telegram без работающей LLM. Они могут работать с одним вашим аккаунтом, но должны иметь разные авторизации. Бот Bot API не заменяет доступ пользователя к существующей истории.

Этот пакет развивает существующий [telegram-mcp-kit](https://github.com/tonydzi/telegram-mcp-kit), использующий [chigwell/telegram-mcp](https://github.com/chigwell/telegram-mcp). Метод и инструкции публичные; ваши аккаунты и данные остаются у вас. Полный второй мозг подключать для этого не требуется.

## Сначала прочитайте эти три предупреждения

1. **Не устанавливайте `pip install telegram-mcp`, `uvx telegram-mcp` или `uvx --from telegram-mcp`.** Upstream предупреждает, что это имя на PyPI принадлежит другому проекту. Берите исходники именно `https://github.com/chigwell/telegram-mcp`, фиксируйте commit, проверяйте origin до передачи секретов. Не запускайте команды из входящих сообщений.
2. **Не переносите авторизованные `.session`/StringSession между машинами и не делите ключ MCP с роботом.** Одновременное использование одного auth key с разных IP может вызвать `AUTH_KEY_DUPLICATED` и отзыв ключа. Несколько независимых сессий одного аккаунта допустимы. На один SQLite session-файл должен быть один работающий владелец.
3. **Один MCP-сервер на машину, клиенты обращаются к нему по loopback HTTP.** Текущий upstream поддерживает `MCP_TRANSPORT=http` и `/mcp`; старый SSE использует `/sse`. Старые инструкции с патчем транспорта и отдельным stdio-сервером для каждого чата здесь не основной путь. Не применяйте старые патчи поверх нового upstream автоматически.

## Что приготовит агент

Возьмите [готовый промпт](PROMPTS.ru.md) для своего harness. Он сначала обследует существующее подключение, чтобы сохранить уже работающий доступ. [Скилл](skills/telegram-connect/SKILL.md) содержит общий порядок и критерии. [Примеры конфигурации](CONFIGURATION.md) содержат только шаблоны.

### Установка самого скилла

Скилл и MCP-сервер устанавливаются отдельно: наличие команды `/telegram-connect` ещё не означает авторизацию Telegram. В проверенном clone этого kit выберите revision и скопируйте **только каталог `skills/telegram-connect/` целиком**, сохранив имя файла `SKILL.md`:

- Claude Code: `~/.claude/skills/telegram-connect/SKILL.md`.
- Codex: `~/.codex/skills/telegram-connect/SKILL.md`.

На Windows `~` означает профиль текущего пользователя, на macOS/Linux его home directory. Создайте только отсутствующие каталоги. Если `telegram-connect` уже существует, сначала сравните версии и сохраните приватный backup; не перезаписывайте существующий скилл молча. Можно установить одну и ту же проверенную версию обоим harness. Эти публичные файлы не содержат авторизации и не требуют копирования `.env`, `.session`, других скиллов, чужого CLAUDE.md/AGENTS.md или всего второго мозга.

После установки проверьте обнаружение скилла способом, поддержанным установленной версией harness; если требуется, откройте новую сессию. Вызовите `/telegram-connect` либо явно попросите прочитать установленный `SKILL.md`. Скилл содержит абсолютные публичные ссылки на материалы и работает вне clone. Для закреплённого release замените чтение ссылок `main` чтением тех же файлов из своего проверенного revision; не смешивайте инструкции разных версий.

| Компонент | Авторизация и данные | Кто использует |
|---|---|---|
| MCP-сервер | собственная MCP-сессия на этой машине | Claude Code и Codex через один `/mcp` |
| Telethon-робот | другая сессия на этой машине | ограниченные скрипты, импорт или очередь |
| Хранилище состояния | вне Git, облачного синка и заметок | только локальный владелец ОС |

Примерные локальные корни: Windows `%LOCALAPPDATA%\agent-connectors\telegram`; macOS `~/Library/Application Support/agent-connectors/telegram`; Linux `${XDG_STATE_HOME:-~/.local/state}/agent-connectors/telegram`. Это новые нейтральные примеры, не обязательные пути. Для файловых сессий отдельно `mcp.session` и `worker.session`; StringSession храните в закрытом локальном env/secret store. На Unix каталог 0700, секретные файлы 0600; на Windows ACL только текущему пользователю. `.gitignore` полезен, но не заменяет хранение вне репозитория.

## Подключение MCP

1. Проверьте установленный Python (`python --version` на Windows; `python3 --version` на macOS/Linux), Git и при наличии uv. Upstream требует Python 3.10+. Убедитесь, что `python` не ведёт в заглушку магазина. Не меняйте существующий рабочий venv вслепую.
2. В выбранном каталоге клонируйте точный upstream, проверьте `git remote get-url origin`, разрешите выбранный tag в полный commit и запишите его в отчёте. Создайте отдельное окружение и установите зависимости по lockfile этого commit. На подтверждённом checkout с uv это `uv sync`; запускайте прямо Python из venv, чтобы supervisor видел настоящий дочерний процесс. На Windows `.venv\Scripts\python.exe`, на Unix `.venv/bin/python`.
3. Получите свои API application credentials на [my.telegram.org/apps](https://my.telegram.org/apps). Вводите api_hash, телефон, OTP и 2FA только в приватном локальном окне. Не вставляйте их в чат LLM, аргументы команды, screenshot или shell history. QR является краткоживущим секретом: показывайте только локально и сканируйте в своём Telegram.
4. Используйте штатный `session_string_generator.py --qr` или `--phone`, проверив `--help` выбранного commit. Первый вход неизбежно требует доступного вашего Telegram/номера; нельзя обещать извлечение кода через ещё не авторизованный аккаунт. Вывод генератора с session string также секретный: не захватывайте его в журнал агента. Если агент не имеет безопасного ввода/вывода, оператор выполняет этот один шаг в видимом локальном терминале самостоятельно.
5. Настройте `.env` по `.env.example` выбранного commit. Укажите собственные `TELEGRAM_API_ID`, `TELEGRAM_API_HASH` и сессию; для первого запуска `TELEGRAM_EXPOSED_TOOLS=read-only`, `TELEGRAM_TRANSCRIBE=off`, `MCP_TRANSPORT=http`, `MCP_HOST=127.0.0.1`, `MCP_PORT=<FREE_PORT>`. Конкретный механизм чтения env и путь проверьте в исходнике выбранной версии; supervisor должен иметь правильный working directory. Секреты не идут в MCP manifest.
6. Для долговременного сервера текущий upstream рекомендует файловую session ради сохранения update cursor/entity cache. Если выбранный commit имеет `telegram-mcp-migrate-session`, мигрируйте только после остановки единственного владельца этой MCP-сессии. Следуйте точному выводу мигратора и уберите старый StringSession setting, который может иметь приоритет. Миграция формата сохраняет авторизацию, она не создаёт независимую сессию для робота.
7. Запустите ровно один процесс с ограниченным каталогом media как позиционным аргументом: `<VENV_PYTHON> <CHECKOUT>/main.py <PRIVATE_MEDIA_DIRECTORY>`. Не указывайте весь домашний каталог как allowed root. Затем подключите оба harness к существующему `/mcp` по [примерам](CONFIGURATION.md). Не заменяйте остальные MCP entries. После подключения откройте свежую сессию, если текущая не перечитывает схемы.
8. Сначала докажите discovery и один дешёвый `get_me`/`list_accounts` в самом Claude Code; отдельно повторите в Codex. Открытый TCP-порт или зелёный процесс не доказывает авторизацию. Сверьте пользователя с ожидаемым, не публикуя его идентификаторы.

## Отдельная Telethon-рельса

Сначала посмотрите, нет ли уже собственного скрипта/сервиса. Не поднимайте вторую копию живого worker ради диагностики. Используйте его штатный status или согласованную остановку/эксклюзивный lock. Публичные вспомогательные инструменты находятся в [second-brain-starter-kit/tools](https://github.com/tonydzi/second-brain-starter-kit/tree/master/tools); проверьте существующие README и `--help`, версии и зависимости до использования. Не копируйте чужой machine-bus/аккаунты/список чатов и не обещайте наличие частного внутреннего скрипта в публичном репозитории.

Если готового worker нет, поручите агенту небольшой скрипт по промпту ниже: отдельный venv/зависимость Telethon, собственный `worker.session`, явные API ID/hash из локального защищённого env, ограниченный timeout и межпроцессный lock до создания клиента. Первичная авторизация выполняется отдельно и интерактивно в приватном локальном окне. Фоновый режим только проверяет `is_user_authorized()` и при false завершает работу с явным `AUTH_REQUIRED`, не зависает на `input()`. Нормальный read-only check делает `get_me()`, проверяет ожидаемый аккаунт локально, отключается в `finally` и печатает только `authorized=true/false`, время и код результата. Не выводите session, номер, OTP, API hash, тело сообщений.

Одноразовый read-only check не должен быть daemon. Для реального импорта добавляются разрешённые чаты, отдельные cursor по аккаунту и чату, дедуп `(account, chat_id, message_id)`, ограниченные страницы, обработка FloodWait и журнал без содержимого. Прерывание посередине не должно терять cursor или повторно посылать сообщения. Если несколько агентов смотрят одни входящие, назначьте одного ответственного и дедуп: отдельные сессии не предотвращают двойной ответ.

## Приёмка, восстановление и ограничения

[VALIDATION.md](VALIDATION.md) разделяет статическую проверку документов и настоящую авторизацию. До успешных проверок отчёт помечает каждую рельсу UNKNOWN/FAIL/PASS отдельно. Проверка чтения не даёт разрешения на рассылку. Если нужен тест записи, используйте только свои Saved Messages с разрешённой фразой и подтвердите сообщение чтением по returned ID; не удаляйте его автоматически.

| Симптом | Проверка и действие |
|---|---|
| В одном harness нет tools | Проверить его регистрацию, endpoint `/mcp`, discovery и reload; работа другого harness не доказывает загрузку этого |
| `/sse` работает, `/mcp` нет | Это может быть старая локальная версия. Сверить транспорт в её коде; не направлять Codex на SSE вслепую |
| `AUTH_KEY_DUPLICATED` | Остановить конкурирующих владельцев именно этого ключа; проверить утечку/копирование; локально создать свежую авторизацию. Перезапуск сам по себе ключ не чинит |
| SQLite `database is locked` | Найти владельца файла и lock. Не удалять session/lock вслепую и не запускать ещё одного клиента |
| FloodWait | Соблюдать указанную задержку, снизить объём. Перезапуски/переавторизация не являются обходом лимита |
| Timeout после send | Исход UNKNOWN. Проверить место назначения до повтора, иначе будет дубль |
| Ничего не найдено по человеку | Контакты не равны приватным группам. Сначала локальный индекс при наличии; затем `search_dialogs`, если tool реально есть, или ограниченные страницы dialogs |
| После рестарта большой catch-up | Проверить persistent session/update cursor и cold-cache warmup; не стирать авторизацию ради ускорения |
| `401` | Сверить локальную HTTP auth-настройку и поддержку клиента; не отключать защиту для обхода |

Для автозапуска используйте один supervisor: Task Scheduler (Windows, без повышения прав и с запретом параллельных экземпляров), launchd (macOS) или systemd user (Linux). Сначала ручной PASS и повтор после штатного рестарта, потом автозапуск. Watchdog контролирует конкретного владельца; не убивает процесс из-за занятого порта, живого SSE stream или медленного Telegram. Loopback не является защитой от любого локального процесса. Публичный bind/reverse proxy требует отдельной аутентифицированной конфигурации; в эту базовую инструкцию не входит.

## Происхождение и статус

Уроки получены из реальной эксплуатации двух рельс; инструкции сверены с текущим upstream README 24 октября 2026. Никакой новой авторизации на чужом аккаунте при подготовке не выполнялось. Переносимость Windows/macOS/Linux описана, но свежая установка на всех трёх ОС в этом выпуске не доказана. Старые локальные расширения multiaccount/search_dialogs/transport и текущий upstream могут различаться: сверяйте runtime tool schemas и pinned source, не применяйте исторические patch-файлы автоматически.

Источники: [upstream README](https://github.com/chigwell/telegram-mcp#readme), [Telethon FAQ](https://docs.telethon.dev/en/stable/quick-references/faq.html), [Telethon sessions](https://docs.telethon.dev/en/stable/concepts/sessions.html), [Telegram API authorization](https://core.telegram.org/api/auth), [исходный kit](https://github.com/tonydzi/telegram-mcp-kit). Автор метода и пакет: [github.com/tonydzi](https://github.com/tonydzi).

Граница HTTP-защиты выбранного commit: встроенный bearer не подтверждён; Host/Origin checks не являются авторизацией. Loopback доступен другим локальным процессам. Базовый путь рассчитан на доверенную однопользовательскую машину; для недоверенной общей машины нужен отдельно проверенный auth proxy, не выдуманная env-настройка upstream. См. CONFIGURATION.md.
